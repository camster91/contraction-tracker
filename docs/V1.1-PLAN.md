## What's already shipped (v1.0.0)

Live on https://contractions.ashbi.ca + relay.ashbi.ca:

- One-tap contraction start/stop, duration + interval tracking
- 5-1-1 pattern detection + audio alert (440Hz pulses + speech)
- Voice control (Web Speech API, on-device)
- State auto-progress: prenatal → labor → postpartum → archived
- Memory book PDF (one-page summary)
- Backup export/import (JSON)
- **Real-time multi-device sync via SSE** — partner, mom, doula all see same data
- **One-link share, 7-day TTL** — works via text/WhatsApp/etc
- **Activity feed** — reactions, text, images, status updates from viewers
- **SSE with adaptive polling fallback** — 1s during contraction, 15s otherwise
- **PIN entry UI** (currently hardcoded off in createShare)
- **Two share "modes"** (UI label only — relay doesn't gate them)
- AAB built, signed, 5.67 MB, new icon. iOS Assets.xcassets updated.

## v1.1 — what to add and why

Built in the order below. Each task has a kanban card on the `contractions`
board with file:line citations.

### Priority 1 — safety + correctness

#### T1. Enforce share mode on the relay (currently a UI lie)

**The problem:** `ShareSheet.tsx:200-222` lets the host pick "Partner — full access"
or "Friends — view only". The relay at `luna-relay/server.js` stores the `mode`
field but never reads it. Anyone with the URL sees the same data.

**Why first:** If a friend forwards the link accidentally, anyone can see
detailed contraction timing data. Real privacy risk in a medical app.

**Scope:**
- `luna-relay/server.js` — `pullContractionsFromRelay` checks share mode,
  returns reduced payload for `friends` (only stats, no individual times)
- New endpoint: `GET /api/shares/:code/stats` returns aggregate only
- Frontend `ShareView.tsx` calls stats endpoint when mode is `friends`
- One link, one mode, set at creation. (Per-recipient mode is T8.)
- Files: `luna-relay/server.js:309-332`, `src/components/ShareView.tsx`,
  `src/lib/relay.ts`

**Effort:** 2-3 hours. One relay change + one client adapter.

#### T2. Host sees viewer activity in real time on the main app

**The problem:** Activity feed messages from viewers come into `ShareView.tsx`
via SSE, but only when the host is on the share view page. The main app shell
(`App.tsx`) doesn't subscribe, so a partner reaction posted while the host is
in the timer view is invisible until they navigate to the share screen.

**Why second:** This is the most-asked-for feature in a multi-user labor app.
"You got this!" reactions from a partner should be visible without tab-switching.

**Scope:**
- New shared `useShareActivitySubscription(code)` hook
- Main app subscribes when `activeShares.length > 0`
- Toast on new message ("Jordan reacted: ❤️")
- Tap toast → opens full share view
- Files: `src/App.tsx`, new `src/lib/useShareActivity.ts`,
  `src/components/ActivityToast.tsx`

**Effort:** 3-4 hours.

#### T3. Wire up the per-recipient clientId for identity

**The problem:** The relay accepts messages from anyone with the share code.
No way to tell "this is the same person across devices" or "this is the
partner who started the labor, not a random viewer."

**Why third:** Builds the foundation for T4 (multi-host) and T8 (per-recipient links).

**Scope:**
- Relay: `messages` table already has `client_id` column, but it's optional
  and not enforced
- Frontend: when entering a name in `ActivityFeed.tsx:248`, generate and store
  a stable `clientId` in localStorage (`olive:client-id`)
- Relay validates `clientId` matches the original `name` for that share
  (or revokes it if name changes mid-session)
- Required for posting in `friends` mode (T1 dependency)

**Effort:** 2 hours.

### Priority 2 — multi-host labor support

#### T4. Partner can start/stop contractions from their device

**The problem:** The `mode: 'track'` field in `lib/shares.ts:9` claims this
exists. The relay doesn't accept it, and the frontend has no UI for it.
Currently only the host device can start contractions.

**Why fourth:** Real labor scenario — host is in too much pain to tap, partner
needs to time them. The whole "team" framing of the app falls apart without this.

**Scope:**
- Relay: `POST /api/shares/:code/contractions` currently accepts from anyone,
  but only the host knows when a contraction is "in progress" (no current
  state). New field: `contraction_start` (timestamp) and `contraction_end`
  (timestamp) as separate events, not full overwrites
- New endpoints: `POST /api/shares/:code/event` with `{type: "start"|"stop"}`
- Frontend `ShareView.tsx` (when mode is `track`): shows big Start/Stop button
  for non-host viewers
- Conflict resolution: if both host and partner start a contraction
  simultaneously, server keeps the earlier timestamp
- Files: `luna-relay/server.js:286-307`, `src/components/ShareView.tsx`

**Effort:** 6-8 hours. Touches DB schema, relay, frontend, conflict logic.

#### T5. Multi-host: anyone with the share can create contractions

**The problem:** Today, only the device that created the share has contractions
in localStorage. If the host's phone dies, the partner's phone sees live data
but can't add anything (T4 partial fix).

**Why fifth:** Depends on T4. Standalone T5 means: any device with the share
code can be a "first-class host" for new contractions. The host designation
is just "whoever pressed Create share link first."

**Scope:** Largely a consequence of T4. If T4's event-based model works,
"creating a contraction" is just "press start on any device." Add:
- `author_client_id` field on contractions (whose timer is this?)
- Display in host view: "Jordan started this one 12s ago"
- Stop button works for whoever started it (server-side auth via clientId)

**Effort:** 3-4 hours (after T4).

### Priority 3 — content + polish

#### T6. Voice memos in the share feed

**The problem:** `VoiceMemoPicker.tsx` exists in the codebase (8 hits in src
tree) but is not wired into the share flow. Users want to send voice
encouragement ("You're doing amazing, breathe with me") in the moment, not
type it.

**Why sixth:** The file is already half-built. Closes a real gap.

**Scope:**
- VoiceMemoPicker → records MediaRecorder audio → base64 (compressed to opus
  if possible, else webm)
- Add `kind: 'voice'` to relay message types
- Relay validates duration ≤ 60s, file size ≤ 500KB
- Frontend plays inline (no autoplay)
- Files: `src/components/VoiceMemoPicker.tsx`, `src/lib/feed.ts`,
  `luna-relay/server.js`

**Effort:** 4-5 hours.

#### T7. Per-recipient share links

**The problem:** One link = everyone sees the same thing. If host wants the
doula to see full data and grandma to see stats only, they need to create
two shares manually.

**Why seventh:** Builds on T1 (mode enforcement) and T3 (clientId identity).

**Scope:**
- Relay: `shares` table gets a parent `share_id` and a `permissions` JSON
  field. Each sub-share is a "viewer invite" with its own code.
- Frontend ShareSheet: "Invite people" replaces single-link flow. Each row
  has a name (e.g. "Doula Sarah") and a mode (full / stats / track).
- Each row gets its own code, its own revoke button
- Files: `luna-relay/server.js:113-180`, `src/components/ShareSheet.tsx`,
  `src/lib/relay.ts`

**Effort:** 8-10 hours. DB migration, relay, frontend rewrite of share UI.

#### T8. Push notifications when viewers post

**The problem:** The host has to be looking at the app to see a partner's
reaction. A quiet partner phone = silent support.

**Why eighth:** Depends on T2 (in-app toasts working) and a service worker
update.

**Scope:**
- Service worker in `dist/sw.js` extended to show notifications on
  `push` event from the relay
- Relay: server-sent `notification` SSE event when a new message arrives
  for a share the user is subscribed to
- Browser Notification API opt-in (request permission on first use)
- iOS Safari PWA limitations: works only if added to home screen
- Android: works in PWA install mode and Capacitor wrapper
- Files: `dist/sw.js`, `src/lib/relay.ts`, `src/components/NotificationOptIn.tsx`

**Effort:** 4-6 hours. iOS PWA notification limits may force a fallback.

### Priority 4 — operational

#### T9. Image storage cap + cleanup

**The problem:** Base64 images in SQLite grow the relay DB unbounded. 20
viewers × 5 photos each × 200KB = 20MB per active share. The 32KB test
DB will become a 500MB production DB fast.

**Scope:**
- Relay: max 50 images per share, 100KB per image, FIFO eviction
- Show "X of 50 photos" in share view
- Optional: add image upload to S3/Cloudflare R2 instead of DB (out of
  scope for v1.1, leave the eviction as the in-scope fix)

**Effort:** 2-3 hours.

#### T10. Custom share TTL in UI

**The problem:** 7-day TTL is hardcoded in `ShareSheet.tsx:77`. A 30-min labor
deserves a 1-day link. A high-risk pregnancy with prodromal labor for weeks
deserves a 30-day link.

**Scope:**
- Add TTL picker to ShareSheet: 1 day / 7 days / 30 days / custom
- `createShare` and `createShareOnRelay` pass through `ttlHours`
- Server already supports custom TTL (`server.js:209`), just need UI

**Effort:** 1 hour.

#### T11. Revoke reason + audit log

**The problem:** The revoke button works but doesn't capture why. If a share
leaks, you can't tell from the audit log what happened.

**Scope:**
- Relay: `revoke_share` records `revoked_at`, `revoked_by_client_id`,
  optional `reason`
- Optional confirmation dialog in ShareSheet: "Why are you revoking?"
  with preset options (link leaked, person left, labor over)
- Audit query endpoint for the host to see who opened when

**Effort:** 3-4 hours.

### Out of scope (intentionally deferred)

- **Voice / video calls between host and viewers** — that's a different
  product (Whereby, Daily.co territory). Don't build it.
- **End-to-end encryption of contractions** — the relay is HTTPS-only and
  Cam explicitly chose relay architecture. E2EE is a v2.0 architectural
  change.
- **Image-to-S3 migration** — keep DB-stored for v1.1, plan the S3 move
  for v1.2 when DB growth justifies it.
- **Removing the dead PIN UI** — when T1 lands, the relay-side enforcement
  handles access control. The PIN UI can be deleted or repurposed for
  "private share" mode in a follow-up.

## Decision points to revisit

- **Voice memos**: build or skip? `VoiceMemoPicker.tsx` is already there,
  suggesting the original plan was yes. But it's a chunk of work.
- **Per-recipient links vs single link with modes**: the second is simpler
  and gets you 80% of the value. Per-recipient is the full feature but
  doubles the relay complexity.
- **Push notifications on iOS PWA**: Apple has crippled these. Worth the
  effort only if you confirm the labor is happening in an Android PWA
  install or Capacitor wrapper, not iOS Safari.
